# ROADMAP.md — Cryptgrid: Vault of Shadows

Work strictly top-down within a milestone. Each step is a committable vertical slice with acceptance criteria (AC). Don't start a milestone early; don't foreclose one either.

## Milestone 0 — "The Vault Breathes" (target: today)

**Definition of done:** deployed to GitHub Pages; a player can explore vault01 at 60fps, loot floor and alcoves, find a secret switch that opens a secret door, watch vitals decay/restore, and cast Light + Firebolt with runes.

### M0.1 — Scaffold
Monorepo (pnpm workspaces, tsconfig.base strict), `packages/sim` + `apps/game` stubs, Vitest + ESLint (incl. sim import restrictions), `ci.yml` (typecheck+test), commands per CLAUDE.md.
**AC:** `pnpm install && pnpm test && pnpm dev` all work; CI green on first PR.

### M0.2 — Sim core: grid, movement, state
Level JSON parse + validate (LEVELS.md), `GameState`, `tick()`, commands MOVE/TURN with cooldowns, wall collision, seeded RNG util. Author `levels/vault01.json` (~16×16; layout must include: a lever-and-portcullis gate, an alcove room, the secret-switch corridor, an inscription teaching Firebolt, scattered items incl. food/water — see LEVELS.md example ids).
**AC:** Vitest covers: move into wall blocked; turn cycles facing; cooldown rejects rapid moves; level validation catches 3+ authored error cases.

### M0.3 — First render
Textures via `tools/gen-textures` (ASSETS.md), Three.js scene from level data (instanced walls/floor/ceiling), camera at party position, torch point-light + fog.
**AC:** vault01 visibly renders; standing at start position matches expectations; 60fps (spot-check devtools).

### M0.4 — Movement feel
Keyboard mapping → commands; 200ms/150ms tweens with ease-out; input buffer (depth 1) for chained held-key movement; wall-bump nudge.
**AC:** Holding W glides down a corridor without hitching; bumping walls feels like a bump, not a bug. **Human checkpoint: Daniel plays it.** Movement feel is the soul of the genre — tune before proceeding.

### M0.5 — Playwright smoke + deploy
Smoke test (load, `data-ready`, screenshot artifact, fail on console errors); `deploy.yml` → GitHub Pages.
**AC:** Live URL playable on phone-a-friend's machine. *(Deliberately early — everything after this ships continuously.)*

### M0.6 — Party & vitals
Character model, 4-slot party (1 filled: pre-made character "Bram of the Ninth Door" or Daniel's choice). Full progression data model per STATS.md, front-loaded now even though most of it is mechanically inert until later milestones: HP/Mana/Stamina + a merged Hunger/Thirst bar (replaces separate Food/Water) with a hidden Ravenousness tier and an overfeed overflow; the six primary attributes (STR/DEX/CHA/VIT/WIS/INT); all six classes tracked (Fighter/Ranger/Wizard/Priest visible, Rogue/Bard permanently `revealed: false` until M1/M2 add their reveal triggers); hidden per-weapon-type skill stubs; hidden elemental-resistance stubs; sparse spell-mastery tracking shape; armor-tier qualification rules. New `packages/sim/src/character/` (mirrors `level/`, `items/`) and `packages/sim/src/tuning.ts` for every tunable formula (exp curve, decay rates, carry-capacity formula). DOM HUD: **4** vitals bars (not 5) — color-coded, smooth width transitions, Hunger/Thirst with overfeed shown as a second-colored overflow segment and a status label (Gorged…Starving) — plus visible levels for the four revealed classes.
**AC:** Vitest: Hunger/Thirst decays per tick, scaled by Ravenousness tier; status tier transitions match the STATS.md table; at Starving, HP drains. Exp-curve and carry-capacity formulas covered (formulas only — carry capacity isn't enforced until M0.7, nothing exists yet to consume it). Bars visibly move (dev-speed decay flag for testing). Rogue/Bard exist in state but never render on the HUD.

### M0.65 — Character sheet
Compact vitals HUD redesign: renders every *filled* party slot at once (not just slot 0), trimmed padding and shorter bars so up to 4 characters fit on screen together; the Hunger/Thirst status label (Gorged…Starving) moves from its own line to an overlay directly on the bar itself, in a font color that stays legible over any fill color; class levels removed from this compact view. New on-demand character sheet: number keys `1`–`4` open/close/switch a full-panel overlay for that party slot (`Esc` also closes), showing the six attributes (STR/DEX/CHA/VIT/WIS/INT), the four visible classes' **level only** (exp stays hidden — see STATS.md correction below), and an Inventory section that's present but empty, wired up for real once M0.7 has items. Movement input is suppressed while a sheet is open; the sim keeps ticking underneath (vitals still decay in real time) — menus don't pause a real-time dungeon.

Also corrects a documented inconsistency: STATS.md previously said class exp was visible alongside level for the four starting classes; the original design intent was always that exp requires a reveal spell/item (same "requires magic or a specific item" family as Truesight and weapon-skill/resistance/mastery numbers) while level alone is plain-visible. STATS.md's Secrecy section now says this correctly — level and exp were never meant to be revealed together.

**AC:** Pressing `1` opens Bram's sheet; pressing it again closes it; `2`/`3`/`4` show an empty-slot placeholder (no character there yet); switching between slots via number keys works without closing first; `Esc` closes from any state. WASD/QE produce no movement while a sheet is open. Compact HUD is visibly resized/decluttered from M0.6 and reads correctly with the current single filled slot.

### M0.7 — Items & inventory
Item registry gains a required `weight` field and an optional `throwable` flag (a `getItemType()` helper replaces scattered inline `ITEM_REGISTRY[x.type]` lookups), plus the `ConsumableEffect` restructure to `{kind: "food"|"water", amount, bonus?}` already owed from M0.6. Floor items can now sit at any of 5 sub-tile positions per tile — center or one of 4 quadrants (`LevelItem.slot`, optional, omitted = center, offset ±0.75 — `TILE_SIZE/4`, already assumed by `apps/game/src/tuning.ts`'s `CAMERA_PITCH_DEG` comment) — so up to 5 items can coexist on one floor tile; `level/query.ts` gains `findItemAt(level,x,z,slot)` and `findItemById(level,id)`, and `validate.ts` gains an item-slot-collision rule (no two items on the same tile+slot).

Every character gains 2 independent hand slots (`Character.hands: [ItemInstance|null, ItemInstance|null]`) — cross-checked against Milestone 1's already-existing "per-hand cooldowns" combat text, so this isn't new scaffolding, it's the field that milestone already expects to exist. A new **PICKUP** command (`{characterId, itemId}`) moves a floor item into an empty hand of the acting character — resolved via raycast + left-click *or* the existing `F`-interact, both targeting whatever's hit (ARCHITECTURE.md's `userData.entityId` idiom); rejected with a `PickupRejected` event if both hands are full or the item isn't actually on the party's tile. A held item is flagged `throwable` (from its registry type) but no throw action exists yet — that's a later milestone's job, this just keeps the data honest. A new **STOW** command (`{characterId, hand}`, right-click) moves a held item from hand into the shared party inventory — carry capacity (STR-derived, `tuning.ts`) is checked *here*, not at pickup, since holding something in your hand shouldn't count against weight, only committing it to the pack should; the shared pool's capacity is the sum of `carryCapacity(member.str)` across all filled party slots. PICKUP/INTERACT-family commands reuse the party's existing move cooldown (same gate as MOVE/TURN, same precedent as `PartyBumped` reusing it for a non-move outcome); STOW and CONSUME are pure bookkeeping (moving an item you already possess) and have no cooldown.

A new `ActiveCharacterController` (game-side only, not sim state — same category of client-local UI fact as `SheetController`'s "which sheet is open") tracks which party slot's hands respond to clicks, reusing the existing `1`–`4` keys (the digit-lookup table gets factored out of `SheetController` so both share it) — pressing a number sets that slot active unconditionally; a press on an empty slot is a no-op, guarded where the click handler already has `state` in scope. The M0.65 character sheet gains a Vitals-adjacent carry-capacity-vs-carried-weight line and a "Hands" section distinct from Inventory. PICKUP is resolved primarily by tile lookup rather than the raycast alone — an item sitting on the party's own tile is geometrically below the camera's frustum at `CAMERA_PITCH_DEG=12` (it's directly underfoot), so it's never actually raycast-hittable; the raycast hit is kept as a fallback for whatever's visibly centered ahead. Wall features — switches, levers, alcoves, inscriptions — render nothing yet and stay that way; alcove rendering and take/place arrive together with the rest of the wallFeature system in M0.8, not before.

A **CONSUME** command (`{characterId, itemId}`) restores Hunger/Thirst and destroys the item — resolves against an item in that character's own hand *or* the shared inventory (checked in that order), applying `ConsumableEffect`'s `amount` plus its `kind`-specific `bonus` (an instant, small stat bump — food leaning HP, water leaning Stamina — not a timed buff). Triggered by clicking a consumable in the inventory DOM panel or in a character's Hands display on the sheet.
**AC:** Vitest: `findItemAt`/`findItemById` resolve correctly across all 5 slots; an authored slot collision fails validation; PICKUP fills an empty hand and fails (with `PickupRejected`) when both are full or the item isn't there; STOW moves hand→inventory and is blocked once the summed carry-capacity formula is exceeded; CONSUME restores Hunger/Thirst (base amount + kind bonus) and destroys the item, working from either a hand or the shared inventory. In game: pick up two different items into both hands (walk onto their tile, then click or `F` — the item itself is no longer visible once you're standing on it, same as the rest of the genre), stow one, consume the other, and see the character sheet reflect held items, capacity, and vitals correctly.

### M0.8 — Switches, doors, secrets
At least 3 visually-distinct base wall textures, not one uniform brick pattern — irregular stone gives a secret switch more than one plausible place to hide, instead of players learning to scan for "the one weird brick." Two new base variants (`wall_fieldstone`, `wall_hewn`, per ASSETS.md) join today's `wall_stone`, **each with its own dedicated secret-switch pairing** — a secret behind rough-hewn stone gets the rough-hewn tell, not the ashlar one. `buildLevel.ts` picks a variant per wall *cell* (not per face — hashing by the wall block's own `(x,z)`, so all faces of one physical stone agree, never split across a corner) via a small stable integer hash; the same level always renders identically. `DungeonTextures.wall` becomes `wallVariants: WallVariant[]` (each `{base, secretSwitch}`), and the already-generated-but-never-wired-up `wall_alcove_back.png` finally gets loaded.

wallFeatures render in 3D for the first time at all — switches, levers, alcoves, and inscriptions currently render nothing. `feature_lever.png`/`feature_switch.png` (listed in ASSETS.md's required set since M0.3, never built) get generated now. A new **INTERACT** command (`{characterId, targetId}` — the source doing the interacting, and the feature being acted on) resolves in `tick.ts`: look up the feature by id, confirm the party is standing in its cell, then walk that feature's *already-existing* `targets[]`/`action` fields (the switch→door toggle schema was fully specified from M0.2 on and just never had a resolver) to flip door/alcove state, firing `SwitchActivated` plus `DoorOpened`/`DoorClosed`/`AlcoveRevealed` as appropriate. Doors gain a real slide animation reacting to those events — collision already respects `door.open` today, it just never had anything to trigger it. `AlcoveFeature` gains an optional `hidden` boolean (omitted/false = today's always-visible alcove): a hidden alcove's face renders as an ordinary wall using its cell's own variant hash — **no tell of its own**, only switches get one — until a linked switch reveals it, at which point it swaps to the recessed-niche treatment plus its items. `validate.ts`'s target-resolution check widens to accept alcove ids alongside door ids.
**AC:** Vitest: INTERACT resolves a switch's targets for both the door case and the alcove case; a lever toggles its door open and closed; a closed door still blocks MOVE, now end-to-end triggerable instead of only settable by test fixture; a hidden alcove starts wall-like and reveals via `AlcoveRevealed`; the wall-variant hash returns the same result on repeated calls for the same cell. In game: find a secret switch embedded among 3+ differently-textured walls, interact with it, and watch a door slide open or a hidden alcove reveal its loot. **Human checkpoint: is the secret findable-but-not-obvious?** — now a meaningfully harder bar thanks to wall variety, which is the whole point.

### M0.9 — Runes & first spells
Rune data (24 runes, SPELLS.md), glyph generation, HUD rune panel (click + keys 1–6, backspace/esc), pay-per-rune mana deduction, invoke/fizzle; Light (torch radius boost w/ duration) and Firebolt (sim projectile entity, 1 tile/2 ticks, wall impact event + renderer flash). Each successful cast increments that spell's mastery counter (STATS.md) — tracked now, inert until M1 makes it affect success chance; M0 stays deterministic per SPELLS.md.
**AC:** Vitest: mana deducted per rune press; insufficient mana blocks rune; `Kor Ign Dart` spawns projectile; projectile halts at wall; invalid sequence fizzles (mana lost); casting increments spell-mastery uses. In game: read the inscription, cast your first Firebolt down a dark corridor. That's the money moment — make the projectile glow and light the walls as it passes (point light parented to projectile).

### M0.10 — Editor v1
`apps/editor` per LEVELS.md editor spec: four modes (Terrain/Walls/Items/Features) over one grid, all layers visible at once, only the active mode's layer interactive. Terrain painting keeps `doors[]` in sync automatically. New in this milestone: `LevelJSON` gains an optional `wallOverrides` field (`{x, z, variant}`) that forces a specific wall look at a specific cell, overriding M0.8's deterministic hash — `packages/sim` gains `resolveWallVariant()` (override-aware) alongside the existing `autoWallVariant()`, and `buildLevel.ts`/`features.ts` in `apps/game` now resolve through it so an authored override actually renders. A contextual property panel edits whatever's selected (door/item/feature/start); a live JSON pane runs `validateLevel()` on every edit and lists errors inline; New/Import/Export/Load-vault01 plus `localStorage` autosave round out the file flow. `tools/viteSharedData.mjs` is extracted so both `apps/game` and `apps/editor` serve `/levels/*`/`/assets/*` identically instead of duplicating the plugin. `levels/vault01.json` grows a new small room (a lever-gated storage nook south of the existing SE chamber) plus 3 authored wall-texture overrides, giving the editor's own dogfood level something the auto-pick alone never produces.
**AC:** Vitest: `resolveWallVariant` prefers an authored override over the auto-pick and only for the cell it's authored at; `validateLevel` catches an override on a non-wall cell, an unknown variant id, and a duplicate override at one cell. Round-trip: edit vault01 in the editor → export → game loads it → change persists — verified live via Playwright (not just typecheck/build): painted terrain, placed an item and a feature, cycled a wall override, selected each entity type back out of the grid, exported a real file download, and confirmed a deliberately-broken item (placed on a wall cell) shows up in the validation list. Two of the three markers item slots and feature ticks used to place were themselves unclickable in their empty state (an SVG `fill:none`/thin-stroke hit-testing gap) until that same Playwright pass caught it.

### M0.11 — Wall texture rework + item/interaction feedback polish
A visual/UX pass on two systems that worked mechanically but read badly. **Walls**: M0.8's 3 textures, picked per-cell by an unrelated hash, never actually blended at their boundaries — reworked into 3 deliberately different types (`stone` clean ashlar, `fieldstone` irregular, `thinbrick` — new, replaces the retired `hewn`) plus a dedicated single-wall-width transition texture for every pairing, editor-authored via `wallOverrides` (still 3-way auto-pick only, unaware transitions exist). Each base type also grows from 1 to 2 secret-tell variants — a conspicuous carved-recess and a subtle grunge-blending mark, built from a reference screenshot — deterministically chosen per switch from its own id (`stringHash`, `packages/sim/src/hash.ts`); all 3 base types also gain a moss/water-stain atmosphere pass (`moss()`/`streaks()` in `tools/gen-textures/pixel.mjs`). **Items**: floor and alcove-shelf items move from always-camera-facing billboard sprites to flat ground-plane quads with foreshortened art (correct perspective from any angle for free, the same way the floor already gets it — this is *why* billboards read as floating, not just an art-quality problem), redrawn with real gradient shading and a baked AO edge instead of a flat silhouette, sized per item type instead of one uniform scale. Picking up an item now shows it following the cursor (`heldItemCursor.ts`) so a pickup is never ambiguous. Pickup range tightens from strict same-tile equality to a distance check (`PICKUP_RANGE_TILES`, `packages/sim/src/tuning.ts`) covering your own tile plus the near half of the next one; a continuous per-frame hover raycast (`hoverHighlighter.ts`, new — today's raycasting is click-only) lights up in-range items light blue and secret switches light yellow while the reticle is on them, hover-only with no persistent "discovered" state. **Follow-up fix (same milestone):** the item slot system dropped its `"center"` option — a center-slotted item was always exactly 1 tile from any neighbor's own center (outside `PICKUP_RANGE_TILES` no matter what) and sat below the camera frustum while standing on it, so it was reachable only via the blind F-key/click fallback and could never show the new hover glow. `ItemSlot` is now the 4 quadrants only; a slot-less item resolves deterministically to one of them from its own id (`resolveItemSlot`, `packages/sim/src/level/query.ts`), so every item — authored or default — has a genuine near-half reachable from the adjacent tile.
**AC:** Vitest: `resolveWallVariant` still only ever auto-picks among the 3 base looks, never a transition; `validateLevel` accepts all 6 variant ids as valid overrides; `resolvePickup`'s distance check accepts own-tile and the near half of an adjacent tile, rejects the far half. In game (verified live via Playwright, not just typecheck/build): a wall boundary using an authored transition renders as a deliberate blended seam, not a hard cut; a secret switch's conspicuous/subtle tell is generated from and matches the reference mechanism; picking up an item shows it on the cursor; items visually sit grounded with correct perspective from multiple viewing angles, not floating; the blue hover outline appears exactly within pickup range and nowhere beyond it; a secret switch tints yellow on hover and clears when not.

*(Polish on already-shipped M0 systems, not new mechanics — same "may slip without shame" latitude as M0.10.)*

## Milestone 1 — "Something in the Dark"
Monsters (grid AI: patrol/chase/attack, tile occupancy, CHA-weighted targeting per STATS.md), melee **and ranged (bow)** combat (per-hand cooldowns, front/back rank rules — ranged is Ranger's entire exp source, so it lands here, not later), damage/death/loot, floor triggers + pressure plates + pits, keys **and lockpicking** on locked doors (first successful pick reveals the Rogue class), a poison status effect (groundwork for Rogue's identity, pairs with M2's throwing items), SFX pass, 2–3 more spells (Frostbolt, Mend, Healmist). Weapon-skill growth, STR/DEX damage/dodge, and elemental resistances (STATS.md) all go live here — this is the first milestone anything actually reads them. Spell mastery starts affecting cast-success chance, fulfilling SPELLS.md's deferred "character skill/fizzle-chance systems come later" line. Multi-floor levels + stairs, editor: spawns/triggers/playtest button.

## Milestone 2 — "The Long Delve"
Per-character paper-doll inventory + equipment (armor tiers from STATS.md become wearable here, not just qualified-for), character creation/party of 4, a bard instrument item (first use reveals the Bard class), save/load (runtime delta serialization), rest system, hunger/thirst tuning pass (Ravenousness-tier-shifting effects, status-revealing magic items), more essences/forms live, Truesight + subtle-secrets economy, throwing items, doors destructible, content: 4-floor vault campaign, Kenney prop set-dressing pass, ambience audio.

*Exploratory, unscheduled:* a CHA-driven vendor/haggling economy (STATS.md) has no committed milestone — M2 is its earliest plausible home given the equipment/economy focus above, but this is a candidate to revisit once M2's scope firms up, not a bullet to build against yet.

## Milestone 3 — "Delve Together"
`apps/server`: Colyseus room wrapping the sim; command transport; client prediction for own movement; lobby/join-by-code; party = one character per player; Docker → AWS Fargate (ALB, WebSockets); Pages client pointed at server for MP mode while solo remains fully offline.

## Milestone 4 — "Beyond the Browser"
Tauri wrapper → Steam build; gamepad support; options/keybinding UI; Capacitor experiment for mobile w/ touch D-pad + tap-to-interact; performance/battery pass.
